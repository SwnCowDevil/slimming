# 孕期版产品与数据架构设计文档

## 1. 文档目的

本文档定义如何在现有 `slimming` 项目上，将产品从“成人减重管理”升级为“孕期家庭饮食管理”，并同步改造原生微信小程序、FastAPI 后端和数据库。

本次不推倒重写。保留现有微信登录、内部用户 ID、食品成分数据、饮食记录快照、体重记录、食谱基础和部署能力，通过 Alembic 增量迁移加入孕期档案、家庭授权、自定义餐次、孕期规则版本和审计能力。

## 2. 已确认决策

### 2.1 产品范围

- 当前版本只覆盖孕期。
- 备孕和产后不进入当前版本，也不在导航和文案中预告。
- 孕妇是数据所有者和主要使用者。
- 伴侣使用独立微信账号，在孕妇授权后参与采购、烹饪和代记录。
- 孕妇可随时查看、收紧或撤销伴侣权限。
- 产品定位是日常饮食记录、家庭协作和信息辅助，不提供诊断、治疗、用药或产检结论。

### 2.2 正式技术栈

- 前端：`miniprogram/` 下的原生微信小程序，使用 WXML、WXSS 和 JavaScript。
- 后端：`backend/` 下的 FastAPI、SQLAlchemy 和 Pydantic。
- 数据库：本地 SQLite，生产 PostgreSQL，结构变更统一使用 Alembic。
- 日历：`wx-calendar`，由项目封装层控制尺寸、标记和主题。
- 图表：`wx-charts`，页面不直接散落实例配置。
- `prototype/` 中的 HTML/React 只是可交互设计参考，不是正式小程序实现，不进入微信小程序构建产物。

### 2.3 设计稿优先级

当历史文档或原型出现冲突时，按以下顺序处理：

1. 本文档决定孕期产品范围、业务规则、数据归属、权限、API 和迁移方式。
2. `2026-08-27-pregnancy-recipe-tab-redesign.md` 决定“食谱”Tab 的页面结构与视觉。
3. 后续孕期 HTML/React 原型决定“今日、记录、趋势、家庭”的信息层级和视觉方向。
4. 旧减重规格只能作为已有技术能力参考，其减重目标、热量赤字、极低热量和孕期全量拦截规则不适用于新版产品。

## 3. 产品定位与成功标准

### 3.1 产品定位

产品围绕一个稳定闭环设计：

> 建立孕期档案 → 查看今日餐单 → 记录实际饮食与感受 → 家庭协作采购和烹饪 → 回顾长期趋势 → 在明确安全边界内获得辅助建议。

产品不以“少吃”、“减重”或“每日热量缺口”为核心，而是强调：

- 饮食规律；
- 食物多样性；
- 真实记录而非完美执行；
- 过敏、忌口和食品安全；
- 家庭分工；
- 对异常症状及时停止普通建议并提示就医。

### 3.2 首版成功标准

- 用户在 3 分钟内完成孕期建档，进入“今日”页。
- 用户可在 30 秒内记录一项已有食物或食谱。
- 用户可为早餐、加餐、午餐、晚餐等餐次自定义名称、时间和顺序。
- 孕妇可在 1 分钟内邀请伴侣，并明确选择共享范围。
- 孕妇撤销权限后，伴侣不能再读取或写入被撤销的数据。
- 任何 AI 输出均不能自动修改正式饮食记录、孕期档案或权限。
- 微信审核文案中不出现治疗承诺、疾病诊断、用药建议、胎儿状态预测或孕期减重承诺。

## 4. 用户、角色与数据所有权

### 4.1 孕妇

- 拥有孕期档案、饮食记录、体重、今日感受、分析和家庭授权数据。
- 可创建、修改和结束孕期档案。
- 可邀请、停用或移除家庭成员。
- 可分别授权“查看餐单”、“勾选采购”、“更新烹饪状态”、“代记饮食”和“查看趋势摘要”。
- 预产期、详细体重、感受记录和 AI 对话默认不向伴侣共享。

### 4.2 伴侣

- 必须使用自己的微信身份登录，不得复用孕妇 Token。
- 只能访问当前有效授权中声明的数据。
- 代记饮食时，数据仍归属孕妇，但操作人记录为伴侣。
- 不能修改预产期、过敏源、孕期档案、规则版本或数据共享权限。

### 4.3 内容管理员

- 不通过小程序普通用户 API 管理食谱。
- 可通过受保护的导入和管理流程更新食品数据、食谱、食品安全标签和推荐规则。
- 内容发布必须保留版本、来源、审核状态和操作人。

## 5. 信息架构与页面设计

底部导航使用五个 Tab：

1. **今日**：孕周摘要、今日感受、今日餐单、采购和烹饪准备。
2. **记录**：日历、餐次、食物、份量、代记人和今日感受。
3. **食谱**：沿用现有正式小程序的食谱页结构和样式。
4. **趋势**：体重长期变化、记录连续性、食物多样性和周期回顾。
5. **家庭**：家庭协作、孕期档案、过敏忌口、授权、隐私和账号设置。

AI 不占用独立 Tab，只在需要的上下文中以小型入口出现。

### 5.1 今日 Tab

使用后续孕期版原型的轻量视觉。模块顺序：

1. 孕周与日期，不显示减重计划天数。
2. 今日感受：正常、有点恶心、反酸、便秘、没胃口。
3. 今日餐单：每顿餐使用独立浅色背景或边框，餐与餐之间保留明确的上下间距，不使用连续深色时间线。
4. 餐次时间可点击编辑，使用 24 小时制并由服务端持久化。
5. 餐次状态：待准备、烹饪中、已吃过。
6. 今日需要准备：采购清单和烹饪任务。
7. 今日关注：一条审核过的轻量提示。

今日页不再把“剩余可摄入热量”作为首屏主视觉，不显示深色热量卡或赤字警告。

### 5.2 记录 Tab

- 页面结构和视觉使用后续孕期版设计。
- 顶部使用经项目封装的 `wx-calendar`，默认是紧凑周视图，用户手动展开月视图。
- 已完整记录、部分记录和无记录使用形状和浅色同时区分。
- 当日记录按餐次排列，显示餐次时间、食物、份量、备注和操作人。
- 记录方式保留食物搜索、最近吃过、食谱加入和拍照候选；拍照结果必须经用户确认后才保存。
- 感受记录是生活记录，不输出疾病判断。

### 5.3 食谱 Tab：保留原小程序设计

食谱 Tab 是本次的明确例外：**不使用后续 HTML/React 原型中的食谱结构和样式**。

必须沿用当前原生小程序食谱页：

1. 原生导航栏标题“健康食谱”。
2. 页内“健康食谱”标题、推荐副标题和右侧搜索按钮。
3. 横向筛选：全部、15 分钟快手、高蛋白、轻素食。
4. “智能推荐”或“筛选结果”分区标题。
5. 单列大图食谱卡，显示菜名、热量、时长和特点。
6. 整卡进入现有食谱详情页。

不新增食谱科普横条、大尺寸 AI 模块、双列小卡、卡片收藏悬浮按钮或广告位。孕期化只改变后端筛选条件、食谱内容、安全标签和推荐文案，不改变页面核心结构与视觉语言。

### 5.4 趋势 Tab

- 页面结构和视觉使用后续孕期版设计。
- 周期支持 7 天、30 天和 90 天。
- 体重趋势只展示真实记录和平滑趋势，强调长期变化，不根据单日波动给出好坏判定。
- 食物多样性按谷薯、蔬菜、水果、蛋奶、肉豆等食材类别统计，不生成缺乏来源的综合健康分。
- 记录连续性由 `wx-calendar` 日期标记表达，不用 `wx-charts` 伪造热力图。
- 跨日趋势使用 `wx-charts` 项目封装组件；空数据和单点数据不进行趋势外推。
- AI 只总结服务端已计算的事实，不自行生成体重目标或营养数字。

### 5.5 家庭 Tab

- 使用后续孕期版原型的轻量视觉。
- 未绑定时先解释共享范围，再创建微信邀请。
- 已绑定时展示成员、今日任务、权限管理和撤销入口。
- 孕期档案、过敏与忌口、隐私、数据来源、账号与删除数据入口收纳在此 Tab，不再另设“我的”Tab。
- 伴侣看到的是授权后的家庭任务视图，不是孕妇全量个人中心。

### 5.6 全局视觉约束

- 主色只使用浅绿、浅蓝、浅黄和浅橙做小面积状态区分。
- 不使用大面积深绿、深蓝灰、黑色卡片或高对比渐变。
- 页面底色接近白色或暖白；功能区优先通过留白、浅色底和间距建立层级。
- 必要的餐次、权限、表单和结果区增加边框或背景；纯文字、页头和连续导航不滥用边框。
- 正文使用常规字重，只在页面标题、模块标题和核心数值上使用中等字重。
- 正文建议 14–16px，次要文字 12–13px，模块标题 17–20px，页面标题 22–24px；小程序以对应 rpx 实现。
- 必要按钮保持 44px 可点击高度，但不因可点击高度放大文字。
- 颜色不作为唯一状态识别，同时使用文字、图标或形状。

## 6. 核心业务流程

### 6.1 首次建档

1. 微信登录并创建内部 UUID。
2. 用户主动授权昵称和头像；未授权不阻塞基础使用。
3. 填写预产期、身高、孕前体重、当前体重、日常活动、过敏、忌口和偏好。
4. 说明预产期、体重和饮食属于敏感健康数据及其用途。
5. 创建孕期阶段和默认餐次时间。
6. 生成第一个“今日”餐单；不生成减重速度、减重日期或热量赤字。

孕周在服务端根据预产期和当地日期动态推导，不作为可独立修改的持久化真值。修正孕周时实际修改预产期并留下审计事件。

### 6.2 自定义餐次和时间

- 默认餐次可包含早餐、上午加餐、午餐、下午加餐和晚餐。
- 用户可修改显示名称、时间和排序，可停用某个餐次。
- 时间保存为用户时区下的 `HH:mm`，并在数据层保留用户时区。
- 记录餐次优先关联 `meal_schedule_id`，不再只依赖 `breakfast/lunch/dinner/snack` 四个枚举。
- 历史记录保留当时餐次名称快照，后续修改餐次名称不改写历史。

### 6.3 家庭绑定

1. 孕妇选择共享范围。
2. 服务端创建一次性邀请，保存邀请令牌哈希、有效期和发起人。
3. 伴侣使用自己的微信账号登录后接受。
4. 服务端验证邀请未过期、未使用且接受人不是发起人。
5. 建立家庭成员关系并写入授权事件。
6. 每次读写请求都在服务端校验当前成员关系和具体权限，不信任前端传入的角色。

默认邀请只开放“查看餐单”、“查看/勾选采购”和“更新烹饪状态”。“代记饮食”和“查看趋势摘要”必须由孕妇另行主动开启。

### 6.4 饮食记录

1. 用户选择食物、食谱或拍照候选。
2. 用户校正名称、份量和餐次。
3. 服务端从本地食品数据计算营养，不接受前端提交的热量为真值。
4. 保存营养快照、数据集版本、数据所有者、操作人和幂等键。
5. 返回新的当日汇总。

家庭成员代记时，`subject_user_id` 为孕妇，`created_by_user_id` 为操作的家庭成员。

## 7. 营养、食谱和推荐边界

### 7.1 数据分层

食品成分与孕期指导必须分层：

1. **食品成分层**：TKA/TAP 相关数据适配器和经许可导入的本地食品成分数据。
2. **孕期规则层**：项目自有、有来源、可版本化的孕期营养和食品安全规则。
3. **审核内容层**：审核后的食谱、替换关系、食材安全标签和用户提示。
4. **个人记录层**：用户已确认的饮食、体重、感受和偏好。

TKA/TAP 只能作为食品成分来源或交互参考，不能单独决定孕期建议。在未取得可稳定使用的官方 API 或数据授权前，禁止在用户请求链路实时爬取网页。

### 7.2 营养目标

- 不再使用“维持热量 - 500 kcal”的减重规则。
- 不把 BMI 或 BMR 作为孕期首屏的执行目标。
- 目标计算必须记录规则版本、依据来源、生效时间和输入快照。
- 孕期营养展示优先使用均衡结构、食物多样性和安全提示，不对单日数值作惩罚式评价。
- 如果未配置经审核的孕期目标规则，系统只展示实际记录，不显示伪造的“目标达成率”。

### 7.3 食谱营养与安全

- 食谱的热量和营养由其食材、克数和当前数据集计算，不由 AI 或前端手写为权威数值。
- 发布食谱时保存营养快照，已加入记录的历史食谱不因后续数据集升级而变化。
- 安全标签包含完全熟制、巴氏杀菌要求、过敏源、慎用提示和审核来源。
- 数据库不能从食材名称自动推断是否熟制、是否巴氏杀菌或汞风险，这些必须来自经审核内容。
- 食谱推荐在匹配个人偏好前，先执行过敏、忌口、安全标签和内容状态过滤。

## 8. AI 能力和安全策略

### 8.1 首版可用能力

1. **AI 换菜**：从已发布、已通过安全标签和过敏过滤的食谱库中选择替代品。
2. **记录解释**：用通俗语言解释用户已确认的食物和营养数据。
3. **周期回顾**：总结服务端已计算的记录频率、食物多样性和趋势事实。

### 8.2 禁止能力

- 诊断或排除疾病。
- 解读产检报告并给出医疗结论。
- 用药、停药或营养补充剂剂量决策。
- 生成热量、营养、胎儿或体重目标数值。
- 鼓励断食、减重、跳餐或极低热量食谱。
- 未经确认直接写入饮食记录、档案、感受或家庭权限。

### 8.3 安全决策链

AI 请求先进入确定性策略层：

1. 验证当前用户与数据权限。
2. 检查输入是否含严重不适、急性过敏、药物、疾病或其他必须转介的上下文。
3. 限定可用数据范围，并只传入必要数据。
4. 数值和食谱候选由服务端产生，AI 只负责选择或表达。
5. 输出保存为草稿，记录模型名称、提示版本、输入数据范围、规则版本和安全决策。
6. 用户确认后才可执行允许的替换或记录操作。

旧策略中“只要孕期就全量拒绝 AI”将被替换为“孕期专用白名单能力 + 高风险上下文转介”，但不能简单删除孕期安全检查。

## 9. 数据架构

### 9.1 保留的现有表

- `users`：内部用户 UUID、昵称和头像。
- `wechat_identities`：继续通过 `(app_id, openid)` 唯一映射内部用户。
- `foods` 及来源数据表：食品成分和中文别名。
- `recipes` 和 `recipe_items`：食谱与食材。
- `weight_entries`：体重记录基础。
- `meal_entries`：饮食快照基础。
- `ai_drafts`：AI 草稿和用户确认流程基础。

`body_profiles` 作为旧减重档案保留，不在孕期模式中继续计算或展示目标体重、热量赤字和三大营养素达成率。首次迁移不删除该表。

`users` 新增非空字段 `product_mode`，默认值为 `legacy_slimming`。完成孕期建档的同一事务内将其更新为 `pregnancy`；不接受小程序直接修改该字段。

### 9.2 新增表

#### `pregnancy_episodes`

| 字段 | 用途 |
|---|---|
| `id` | UUID 主键 |
| `user_id` | 孕妇用户 ID |
| `due_date` | 预产期 |
| `due_date_source` | 用户填写、修正等来源 |
| `status` | `active` / `ended` / `archived` |
| `timezone` | 用户时区，默认 `Asia/Shanghai` |
| `started_at` | 档案开始时间 |
| `ended_at` | 结束时间，允许为空 |
| `created_at`, `updated_at` | 审计时间 |

同一用户在一个产品环境中最多只有一个 `active` 孕期档案。孕周由 `due_date` 和当地日期推导，不单独持久化。

#### `pregnancy_preferences`

| 字段 | 用途 |
|---|---|
| `pregnancy_episode_id` | 唯一关联孕期档案 |
| `height_cm` | 身高 |
| `pre_pregnancy_weight_kg` | 孕前体重，允许为空 |
| `activity_level` | 日常活动级别 |
| `dietary_preferences` | JSON 偏好 |
| `allergens` | JSON 过敏源 |
| `avoidances` | JSON 忌口 |
| `disliked_foods` | JSON 不喜欢食物 |
| `updated_at` | 最后修改时间 |

当前体重从最新 `weight_entries` 获取，不在多个表重复保存为真值。

#### `meal_schedules`

| 字段 | 用途 |
|---|---|
| `id` | UUID |
| `pregnancy_episode_id` | 所属孕期档案 |
| `code` | 稳定业务标识 |
| `display_name` | 用户自定义名称 |
| `scheduled_time` | `HH:mm` |
| `position` | 当日排序 |
| `enabled` | 是否启用 |
| `updated_at` | 修改时间 |

#### `meal_plan_days` 与 `meal_plan_items`

`meal_plan_days` 按孕期档案和日期唯一，保存计划状态和规则版本。`meal_plan_items` 保存餐次、食谱或自定义菜品、待准备/烹饪中/已吃过状态、负责人、排序和当时标题快照。

#### `daily_wellbeing_logs`

按孕期档案和日期唯一，保存用户选择的日常感受代码和可选备注。数据用于记录、餐单筛选和非诊断性回顾。

#### `family_memberships`

| 字段 | 用途 |
|---|---|
| `id` | UUID |
| `pregnancy_episode_id` | 关联孕期档案 |
| `member_user_id` | 伴侣的独立用户 ID |
| `role` | 首版固定为 `partner` |
| `permission_scopes` | JSON 权限快照 |
| `status` | `invited` / `active` / `revoked` |
| `invited_at`, `accepted_at`, `revoked_at` | 关系时间 |

#### `family_invitations`

保存一次性邀请的令牌哈希、发起人、孕期档案、预设权限、失效时间和使用时间。不持久化明文邀请令牌。

#### `family_tasks`

保存采购、烹饪和其他家庭任务的日期、类型、标题、结构化内容、负责人、状态和完成时间。

#### `consent_events`

保存授权创建、权限调整、撤销、删除和敏感数据共享事件。事件不覆盖更新，保留当时权限快照和操作人。

#### `nutrition_target_snapshots`

保存经审核规则计算出的阶段目标快照，包括生效日期范围、输入快照、能量和已支持营养素、来源和 `rule_version`。如果未配置审核规则，该表不产生伪造记录。

#### `recipe_nutrition_snapshots` 与 `recipe_safety_labels`

- `recipe_nutrition_snapshots` 保存食谱发布时的营养总计、份数、数据集版本和计算时间。
- `recipe_safety_labels` 保存过敏、熟制、巴氏杀菌、慎用、审核来源和发布状态。

### 9.3 现有表的增量修改

#### `meal_entries`

新增：

- `pregnancy_episode_id`，允许为空；
- `subject_user_id`，数据归属人；
- `created_by_user_id`，记录操作人；
- `meal_schedule_id`，允许为空；
- `meal_name_snapshot`；
- `recorded_at`；
- `note`，允许为空。

迁移时将旧数据的 `subject_user_id` 和 `created_by_user_id` 回填为原 `user_id`。过渡期保留 `user_id` 以兼容旧接口，新业务逻辑以 `subject_user_id` 为数据归属依据。

#### `weight_entries`

新增 `pregnancy_episode_id`、`subject_user_id` 和 `created_by_user_id`，同样对旧数据进行回填。

#### `recipes`

保留现有标题、描述、时长、标签和图片，新增内容状态、适用人群标签、内容版本和审核时间。食谱列表 API 返回已计算的热量、副标题、安全摘要和可用筛选标签，以支持原小程序食谱卡。

## 10. API 设计

### 10.1 孕期档案

- `POST /api/v1/pregnancies`：创建孕期档案和偏好。
- `GET /api/v1/pregnancies/current`：返回当前孕期档案、动态孕周和偏好。
- `PATCH /api/v1/pregnancies/current`：修改预产期或偏好，保留审计。
- `POST /api/v1/pregnancies/current/end`：结束当前档案，不自动进入产后模式。

### 10.2 餐次和今日计划

- `GET /api/v1/meal-schedules`
- `POST /api/v1/meal-schedules`
- `PATCH /api/v1/meal-schedules/{id}`
- `GET /api/v1/meal-plans/{date}`
- `PATCH /api/v1/meal-plans/{date}/items/{item_id}`

创建或修改餐次时，后端验证名称长度、`HH:mm` 格式、排序重复和归属权限。

### 10.3 记录

- 扩展现有 `POST /api/v1/meals`，接收 `subject_user_id` 和 `meal_schedule_id`，但必须在服务端重新校验家庭权限。
- `GET /api/v1/meals?date=...&subject_user_id=...`：仅返回当前身份有权访问的数据。
- `PUT /api/v1/wellbeing/{date}`：保存当日感受。
- `GET /api/v1/wellbeing/{date}`：返回当日感受。

所有写接口保留幂等键，家庭代记不改变数据所有人。

### 10.4 家庭

- `POST /api/v1/family/invitations`：孕妇创建一次性邀请。
- `POST /api/v1/family/invitations/{token}/accept`：伴侣登录后接受。
- `GET /api/v1/family/members`：返回当前孕期档案的家庭成员。
- `PATCH /api/v1/family/members/{id}/permissions`：只允许孕妇修改。
- `DELETE /api/v1/family/members/{id}`：撤销授权并写入授权事件。
- `GET/POST/PATCH /api/v1/family/tasks`：在权限范围内管理采购和烹饪任务。

### 10.5 食谱与趋势

- 扩展 `GET /api/v1/recipes`，支持 `max_minutes`、`tag`、`high_protein`、过敏过滤和分页，但不改变前端食谱页的四个筛选项。
- 食谱响应新增 `energy_kcal`、`subtitle`、`safety_summary`、`content_version`。
- 扩展 `GET /api/v1/analytics/summary`，返回体重趋势、记录天数、食材类别多样性和可解释的回顾事实。
- 孕期模式不返回减重热量预算达成率，不调用旧 `body_profiles.daily_kcal` 生成孕期结论。

### 10.6 AI

- `POST /api/v1/ai/recipe-swaps`：从审核后候选集中返回换菜草稿。
- `POST /api/v1/ai/weekly-reflections`：根据服务端汇总的事实返回回顾草稿。
- 继续使用草稿确认模式，但将安全结果扩展为 `allow`、`allow_limited`、`refer_professional` 和 `emergency_guidance`。

`emergency_guidance` 不调用生成模型，只返回经审核的固定安全文案，提示用户停止使用常规饮食建议并及时联系医疗机构或紧急救助。它不提供症状判断或急救操作指导。

## 11. 数据访问与授权规则

所有受保护业务查询必须同时应用：

1. 当前 Token 对应的内部 `current_user.id`。
2. 请求数据归属人 `subject_user_id`。
3. 当前活跃孕期档案。
4. 用户是数据所有者，或存在 `active` 的家庭成员关系。
5. 家庭成员关系包含当前操作所需权限。

前端的 Tab、按钮隐藏和本地缓存不构成权限保护。后端必须在每个读写路由上执行数据级授权。

### 11.1 建议的权限代码

- `meal_plan:read`
- `shopping_task:read`
- `shopping_task:write`
- `cooking_status:write`
- `meal_entry:write_for_owner`
- `trend_summary:read`

首版不向伴侣开放预产期修改、详细体重记录、感受备注、AI 对话、授权修改和删除账号权限。

## 12. 迁移与兼容策略

### 12.1 不直接覆盖

- 不删除旧 `body_profiles`。
- 不把现有减重用户自动转换为孕期用户。
- 不将旧目标体重解释为孕期目标。
- 不覆盖历史饮食和体重快照。

### 12.2 产品模式

在用户层引入服务端可控的 `product_mode`：

- `legacy_slimming`：仅用于旧数据兼容和迁移期。
- `pregnancy`：新用户和已主动完成孕期建档的用户。

新小程序版本默认引导用户建立孕期档案。检测到旧减重档案时，提示用户重新建立孕期档案，不自动带入目标体重和减重热量。

### 12.3 Alembic 迁移顺序

1. `0006_pregnancy_core`：孕期档案、偏好、餐次、感受和产品模式。
2. `0007_family_collaboration`：家庭邀请、成员、权限、任务和授权事件。
3. `0008_tracking_ownership`：饮食与体重的数据所有者、操作人和孕期关联，完成旧数据回填。
4. `0009_meal_plans`：每日餐单、餐单项和家庭采购/烹饪任务。
5. `0010_pregnancy_guidance`：营养目标快照、食谱营养快照、安全标签和规则版本。

每次迁移在生产执行前必须：

- 备份生产数据库；
- 在生产数据副本验证升级时长；
- 校验回填行数、空值、唯一约束和外键；
- 保留可执行的 downgrade 或服务回滚方案；
- 先发布兼容旧表的后端，再发布依赖新接口的小程序。

## 13. 隐私、合规与微信审核

### 13.1 数据最小化

- 只收集实现餐单、记录、趋势和家庭协作所需的孕期数据。
- 不收集产检影像、病历、处方、药物清单或胎儿诊断数据。
- 微信头像和昵称仅在用户主动授权后保存。
- 日志中不记录 `openid`、Token、邀请明文、预产期、完整饮食内容或 AI 对话原文。

### 13.2 用户权利

- 查看当前孕期档案和家庭授权。
- 修正预产期和偏好。
- 结束孕期档案。
- 撤销家庭共享。
- 删除个人数据和账号。
- 在可行范围内导出个人饮食和体重记录。

### 13.3 审核文案约束

可使用：

- “日常饮食记录”
- “已审核食谱筛选”
- “信息仅供日常参考”
- “如有不适，请联系医生或专业人员”

禁止使用：

- “治疗”、“疗效”、“保证”、“预防胎儿问题”
- “孕期减重”、“掉秤”、“燃脂”、“断食”
- “AI 医生”、“AI 诊断”、“代替产检”
- 对恶心、反酸、便秘等感受作疾病判断

## 14. 错误、空状态与离线处理

- 未完成孕期建档：只允许进入建档、隐私和帮助流程。
- 预产期不合理：明确显示输入范围，不自动修正。
- 无食谱匹配：保留原食谱页结构，显示可恢复空状态和“查看全部”。
- 食品数据源不可用：可保存本地草稿，不伪造营养数值。
- 家庭权限已撤销：返回 403 并立即清理伴侣端对应缓存。
- 邀请过期或已使用：不暴露孕妇身份和档案信息。
- 重复提交：使用幂等键返回原结果，不创建重复饮食。
- 图表数据少于两个点：展示原始记录和“继续记录”入口，不连线外推。
- 网络断开：小程序将未提交的餐次和感受保存为本地草稿，恢复网络后由用户确认同步。

## 15. 测试策略

### 15.1 单元测试

- 预产期到孕周和孕期阶段的计算，包括时区和日期边界。
- 餐次时间、排序、停用和历史名称快照。
- 家庭权限决策。
- 食谱过敏和安全标签过滤。
- 食谱营养快照和历史稳定性。
- 体重趋势和食物多样性汇总。
- AI 白名单、限制回答和转介决策。

### 15.2 API 和数据库测试

- 微信身份继续正确映射内部 UUID。
- 孕妇 A 不能读取孕妇 B 的数据。
- 未授权伴侣、已过期邀请和已撤销成员均无法访问。
- 只有查看权限的伴侣不能代记饮食。
- 伴侣代记后，数据所有人和操作人正确分离。
- 幂等键不产生重复餐次。
- Alembic 升级后旧饮食和体重数据行数不变，所有者和操作人回填正确。
- 孕期模式不调用旧减重热量赤字逻辑。

### 15.3 原生小程序验收

- 使用微信开发者工具构建和预览，不以 HTML/React 构建成功代替验收。
- 今日页每顿餐的边界和间距清晰，餐次时间可修改且重启后仍保留。
- 食谱 Tab 结构和视觉与原小程序版一致，不出现孕期 React 原型的科普横条和双列卡。
- 记录页的 `wx-calendar` 周/月切换、日期标记和日期查询正常。
- 趋势页的 `wx-charts` 在安卓和 iOS 真机上清晰，切换周期不重复创建泄漏实例。
- 家庭邀请、接受、代记和撤销完成端到端验证。
- 主流屏幕宽度下不出现大字号、重字重、深色大色块、TabBar 遮挡或内容溢出。

## 16. 分阶段交付

### 阶段 0：契约和数据准备

- 冻结本文档、API 命名和权限代码。
- 备份数据库并建立迁移校验脚本。
- 确认食品成分数据的导入许可和版本。
- 梳理小程序隐私声明和微信审核文案。

### 阶段 1：孕期核心

- 孕期档案、偏好、自定义餐次和感受记录。
- 停用孕期模式的旧减重算法。
- 原生小程序“今日”和“记录”页。

### 阶段 2：食谱和趋势

- 在保留原食谱 Tab 设计的前提下补齐后端热量、副标题、筛选、营养快照和安全标签。
- 完成孕期趋势汇总和 `wx-charts` 封装。

### 阶段 3：家庭协作

- 邀请、接受、权限、撤销和授权事件。
- 采购和烹饪任务。
- 代记饮食的所有者/操作人分离。

### 阶段 4：受限 AI

- 审核后食谱库内换菜。
- 已确认数据的记录解释和周期回顾。
- 安全评测、数值引用校验和微信审核文案复核。

AI 不应在孕期核心记录、食谱和权限未稳定前先行上线。

## 17. 明确不做

- 备孕管理。
- 产后恢复、哺乳或婴幼儿喂养。
- 产检报告解读。
- 胎儿发育预测或健康评分。
- 疾病诊断、治疗、用药或补充剂剂量。
- 孕期减重、断食、轻断食或极低热量计划。
- 伴侣查看全部个人数据。
- 家庭实时聊天、支付、医生预约或在线问诊。
- 在请求链路中实时爬取 TKA/TAP 网页。
- 用 React 或 HTML 替代现有原生微信小程序。

## 18. 整体验收条件

孕期版只有在以下条件全部满足后才能认为完成：

1. 正式产物是 `miniprogram/` 原生小程序和 `backend/` FastAPI 服务。
2. 今日、记录、趋势和家庭采用后续孕期版设计；食谱 Tab 保留原小程序结构和样式。
3. 今日餐单中每顿餐有清晰边界和间距，时间可自定义并持久化。
4. 孕期模式已彻底停止使用旧减重热量赤字和目标体重逻辑。
5. 微信用户身份映射内部 ID，所有个人数据按内部 ID 隔离。
6. 家庭成员使用独立账号，每次数据访问经后端权限校验，撤销后立即失效。
7. 代记数据正确区分“数据属于谁”与“谁执行记录”。
8. 食品成分、孕期规则、审核内容和用户记录分层保存，营养和规则保留版本。
9. AI 只在白名单能力内运行，高风险内容终止并转介，所有可执行结果需用户确认。
10. Alembic 迁移、回填、回滚、权限、幂等、跨用户隔离和原生小程序端到端流程均通过验证。
